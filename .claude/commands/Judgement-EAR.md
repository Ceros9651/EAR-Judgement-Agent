# /Judgement-EAR — 輸出管理 該非判定 事前調査

あなたは輸出管理（EAR／日本の外為法）に精通したエンジニアとして、このリポジトリを走査し、
**社内の該非判定プロセスに提出できる一次調査資料**を作成する。

あなたの成果物は法的判断ではなく、**判定担当者が判断するための材料**である。
断定せず、根拠と確信度を必ず添えること。

## 1. 実行モード

第1引数 `$1` でモードを切り替える。省略時は `quick`。
第2引数 `$2` は走査対象のサブパス。省略時はリポジトリルート（単一リポジトリ前提）。

### `quick`（日常確認用 / 数分）

- 自社コード＋`package.json` の直接依存＋インフラ定義（Dockerfile / IaC）のみ
- Web 検索は行わない
- 出力は **Markdown レポートのみ**（CSV・snapshot は生成しない）
- 目的：新しい依存を入れたとき・PR レビュー時に「規制候補が増えていないか」を素早く見る

### `full`（本番提出用）

- lockfile の推移依存まで全件、インフラ・利用中のマネージドサービス・CDN 経由の外部スクリプトまで対象
- 判断が割れる項目は Web 検索で裏を取る（§7 参照）
- 出力は **Markdown レポート＋CSV＋snapshot.json**
- 目的：社内該非判定に提出する

### `diff`（依存追加時の差分確認）

- 前回の `full` が残した `docs/export-control/snapshot.json` と現状を突き合わせ、
  **追加・削除・バージョン変更のあったものだけ**を Phase 2〜4 にかける
- 詳細は §10

引数が `quick` / `full` / `diff` のいずれでもない場合は、サブパス指定とみなして `quick` で動く。

## 2. 対話のルール

§0 でヒアリングは完了している。**走査開始前の質問は行わない。** 対話が必要になるのは以下の3場面だけ。

### 2-1. 質問の出し方（守ること）

- 質問するときは **必ず `AskUserQuestion` を使い、選択肢を提示する。** 自由記述で投げない
- 選択肢には必ず「わからない／後で確認する」に相当する逃げ道を用意し、
  それが選ばれた項目は**推測で埋めず**レポート §8「要確認事項」に転記する
- 具体名（パス・国名・様式名）は `AskUserQuestion` が自動で出す「Other」で拾う

### 2-2. 前提が現況と違うと分かったとき

走査中に §0 の前提と明らかに矛盾する事実を見つけた場合（例：IaC に海外リージョンがある、
`server-only` の無いブラウザ側で機密性暗号化をしている、等）は、**走査を止めずに最後まで進め**、
レポートに矛盾を明記したうえで、チャットで1問だけ確認する：

- header `前提の更新` — 「§0 の前提と食い違う事実を検出しました。前提を更新しますか？」
  - `前提を更新する（.claude/ear-intake.json に記録）` / `前提は変えない（検出内容を要確認に立てる）` / `詳しく説明してほしい`

「更新する」が選ばれたら、該当項目だけを `AskUserQuestion` で選択肢付きに聞き直し、
`.claude/ear-intake.json` に `{項目, 新しい値, 更新日, コミットハッシュ}` として保存する。

### 2-3. ビルド実測の許可が要るとき

静的解析で配信境界（client / server）を確定できない依存が出た場合のみ、その依存名を挙げて聞く：

- header `ビルド実測` — 「◯◯ の配信境界が静的解析で確定できません。ビルドして実測しますか？」
  - `ビルドして実測する` / `client? として要確認に立てる` / `以降も聞かずに要確認で倒す`

**ビルドコマンドは意図的に `allowed-tools` に入れていない。** 許可された場合のみ実行し、
`許可なくビルドしない`（§11）を満たすこと。

### 2-4. `diff` モードで snapshot が無い / 更新するとき

§10 を参照。

## 3. Phase 1 — インベントリの収集

以下を順に収集する。**存在しないものは「該当なし」と明記**し、勝手に省略しない。

1. **パッケージマネージャの特定** — `pnpm-lock.yaml` / `package-lock.json` / `yarn.lock` / `bun.lockb` のどれがあるか
2. **依存の全量** — `dependencies` / `devDependencies` / `optionalDependencies` / `peerDependencies` を分けて取得。
   `full` では lockfile を直接パースして推移依存も含めた一覧と、その総数を出す
3. **自社ソースコード** — `src/` 配下など。言語・フレームワーク構成（フロント／API／バッチ／Lambda ハンドラ等）を把握
4. **バンドラ設定** — `vite.config.*` / `webpack.config.*` / `next.config.*` / `tsconfig.json` の paths・externals・manualChunks
5. **インフラ定義** — `Dockerfile`（ベースイメージのタグを含む）／`docker-compose.*` ／ CDK・Terraform・CloudFormation・SAM・Serverless Framework
6. **利用中のクラウドサービス** — IaC とコード内の SDK 呼び出しから、実際に使っている AWS / Google Cloud のサービスを列挙
7. **外部配信スクリプト** — `index.html` や CSP 設定にある CDN 経由の `<script src>`、フォント、解析タグ、決済 SDK 等
8. **CI/CD とビルド成果物** — GitHub Actions 等の定義。何がビルド成果物に入るか

> `devDependencies`（eslint / prettier / vitest 等）は成果物に含まれないため原則対象外だが、
> **ビルド成果物に混入していないかを一度だけ確認**し、混入がなければ「対象外」として一括処理してよい。

単一リポジトリ前提のため、走査対象はリポジトリルート固定。`$2` が与えられた場合はその配下に絞り、
**絞ったこと・絞った範囲をレポート §1 に明記する**。

## 4. Phase 2 — 配信境界の判定【このコマンドの核心】

各依存・各モジュールを、次の3つに必ず分類する。**この分類が EAR 判定の結論を左右する。**

| 区分       | 定義                                                                         | 輸出管理上の意味                                                                            |
| ---------- | ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| **client** | ビルド後のフロントエンドバンドルに含まれ、顧客のブラウザにダウンロードされる | 実質的にソフトウェアのコピーが相手に渡る。**5D002 / 5D992 の論点が正面から立つ最重要区分**  |
| **server** | サーバ側（Lambda / ECS / Cloud Run 等）でのみ実行され、顧客に渡らない        | SaaS としてのサービス提供に留まる。export 該当性は低いが、みなし輸出・技術提供の論点は残る |
| **build**  | ビルド時・開発時のみ使用し、成果物に含まれない                               | 原則対象外（要：混入確認）                                                                  |

### 分類の手順（推測で決めないこと）

1. エントリポイント（`src/main.tsx` 等）から **実際の import グラフを辿る**
2. `package.json` の `dependencies` に入っていても、フロントから import されていなければ client ではない
3. 逆に `devDependencies` にあってもバンドルされる設定なら client
4. SSR / Next.js の場合は、サーバ専用領域（`server-only`、Route Handler、`getServerSideProps` 等）とクライアント領域を区別する
5. 判定できない場合は §2-3 の許可質問を出す。許可が下りなければ `client?` として
   **保守的に client 側に寄せ**、「要確認」に立てる

## 5. Phase 3 — 規制対象技術の検出

以下のカテゴリを、**コードとインフラの両方**に対して走査する。
ヒットした場合は必ず `ファイルパス:行番号` の形で検出箇所を記録する。

### 5-1. 暗号・情報セキュリティ【最優先。ここが該非判定の主戦場】

EAR では Category 5 Part 2（Information Security）、外為法では輸出令別表第1の **9の項**（情報通信・情報セキュリティ）に対応する。

走査対象：

- **暗号を自前実装・ラップしているコード** — 最も重要。`encrypt` / `decrypt` / `cipher` / `AES` / `RSA` / `ECDH` / `KDF` 等の識別子と、その実装本体
- **暗号ライブラリ** — `crypto-js`, `node-forge`, `forge`, `elliptic`, `tweetnacl`, `libsodium-wrappers`, `sjcl`, `jsencrypt`, `asn1.js`, `node:crypto`
- **ハッシュ／パスワード** — `bcrypt`, `bcryptjs`, `argon2`, `scrypt-js`, `hash-wasm`
- **トークン・署名** — `jsonwebtoken`, `jose`, `jws`, `@panva/*`, OIDC / SAML ライブラリ
- **WebCrypto API** — `crypto.subtle.*` の直接呼び出し
- **鍵管理サービス** — AWS KMS / Secrets Manager / CloudHSM / ACM、Google Cloud KMS / Secret Manager
- **クライアントサイド暗号化・E2EE** — ブラウザ側で機密性のための暗号化をしている箇所（**最も該当性が高い**）
- **ハードコードされた仕様** — `AES-256-GCM`, `RSA-2048`, `P-256`, `secp256k1`, `Ed25519` 等のアルゴリズム名・鍵長
- **暗号解析・鍵破り機能**（5D002.c.1 相当） — 通常の Web アプリには無いはずだが、無いことを明記する
- **VPN / トンネリング / プロトコル実装**

#### 申告値（§0-2）との突き合わせ【必須】

申告は「認証・署名のみ、機密性の暗号化は無し」である。走査結果を必ずこれと突き合わせる：

| 走査結果                                        | 扱い                                                                                          |
| ----------------------------------------------- | --------------------------------------------------------------------------------------------- |
| 認証・署名・ハッシュ用途の暗号のみ検出          | 申告と一致。Cat.5 Part 2 の Note 群・ancillary の除外方向で整理し、根拠を書く                 |
| **機密性目的の暗号化を検出**                    | **申告と矛盾。レポート §2 の冒頭に明記**し、5D002 の論点を正面から立てる。確信度は下げない      |
| 判断がつかない（用途不明の `encrypt` 呼び出し） | `要確認` に立て、検出箇所と「何を確認すれば決まるか」を書く。申告に寄せて「認証用だろう」としない |

#### 検出しただけで終わらせないこと（誤検知対策）

暗号ライブラリの import を見つけたら、**必ず呼び出し箇所を読んで次を確定させる**：

| 確認項目     | 記録する内容                                                                                             |
| ------------ | -------------------------------------------------------------------------------------------------------- |
| アルゴリズム | AES / RSA / ECDSA / SHA-256 等                                                                           |
| 鍵長         | 対称何ビット、非対称何ビット、楕円曲線名                                                                 |
| 用途         | ①**機密性**（データを秘匿）②認証・完全性のみ ③デジタル署名のみ ④パスワードハッシュのみ ⑤DRM・著作権保護 |
| 位置づけ     | 主要機能か、付随機能（ancillary）か（§0-2 の申告は「付随機能」。異なる実態なら明記）                     |
| 配信境界     | client / server / build                                                                                  |

**②〜⑤は EAR の Cat.5 Part 2 の Note 3・Note 4 や ancillary cryptography の除外に乗る可能性が高く、
外為法側にも対応する除外がある。①だけが本丸である。** この区別を潰さずにレポートに書くこと。

### 5-2. AI・先端計算

- 独自の学習済みモデル重みをリポジトリに含む／配布しているか
- GPU 推論 SDK（CUDA, cuDNN, TensorRT, ROCm）の同梱
- 外部 AI API（Amazon Bedrock, Vertex AI, OpenAI API 等）の**呼び出しのみ**か
  → 呼び出しのみなら **非該当の根拠を1行**だけ記載する（§0-4）。モデル重み・推論 SDK の同梱があれば1行では済ませない
- 3A090 / 4A090 系（先端半導体・計算機）は通常ハードウェアの話であり SaaS アプリでは無関係だが、**無関係であることを明記**する

### 5-3. その他のカテゴリ（該当が無いことの確認も成果物）

- **侵入ソフトウェア**（4A005 / 4D004 相当）— 脆弱性スキャン・エクスプロイト・監視機能
- **測位・航法**（Category 7）— 高精度 GNSS 処理、慣性航法
- **通信インフラ制御**（Category 5 Part 1）— 通信傍受・トラフィック解析
- **暗号以外の情報セキュリティ** — フォレンジック、ネットワーク侵入検知

### 5-4. マネージド認証基盤・クラウドサービス

§0-4 のとおり、**常にベンダー公表の ECCN を調べて記載する**。

- 対象：Cognito / Firebase Authentication / Auth0 / Okta 等の認証基盤、KMS・Secrets Manager 等の鍵管理、
  その他 IaC とコードから検出したマネージドサービス
- `full` ではベンダーの輸出管理ページを Web 検索し、**ECCN・URL・取得日**を記録する
- 公表 ECCN が見つからなかった場合は `要確認` とし、「ベンダーに照会が必要」と書く。**推測で ECCN を書かない**
- CSV では区分 `外部サービス` として1行ずつ立てる

### 5-5. 取引規制（品目ではなく相手の規制）

品目分類とは別軸なので、レポートでは**必ず別セクション**にする。

- 禁輸国（EAR Country Group E:1：キューバ・イラン・北朝鮮・シリア等）からのアクセス遮断の有無
- Entity List / Denied Persons List / SDN リストのスクリーニング有無
- 利用規約上の輸出管理条項の有無
- ロシア・ベラルーシ向けの追加規制への対応

> 提供先は国内のみ（§0-1）だが、**SaaS は技術的には国外からアクセスされうる**。
> アクセス制御が実装されているかどうかを事実として記録すること（「国内のみだから不要」で済ませない）。

## 6. Phase 4 — 該非判定

### 6-1. EAR 側のデシジョンツリー

各対象について、上から順に評価する。

1. **EAR の対象か** — 米国原産のソフトウェア／技術か、または米国原産のものを組み込んでいるか。
   非米国原産なら、de minimis（§734.4、原則25%・E:1向け10%）の検討が必要かを記す
2. **公開されているか** — 公開 OSS は §734.3(b)(3) / §734.7 により "not subject to the EAR" となりうる。
   ※暗号ソフトの §742.15(b) の BIS/NSA への通知義務は**公開する側**の義務であり、利用する側は通常負わない。この区別を混同しないこと
3. **暗号機能を持つか** — 持たない → **EAR99** 濃厚
4. **除外規定に乗るか** — 認証・署名のみ／完全性のみ／パスワードハッシュのみ／DRM／ancillary cryptography（Cat.5 Part 2 の Note 群）→ 対象外方向
5. **機密性のための暗号で、技術的閾値を超えるか** — 対称56ビット超、非対称の素因数分解512ビット超、離散対数512ビット超、楕円曲線112ビット超 → **5D002** 方向
6. **マスマーケット要件を満たすか**（Cryptography Note / §740.17(b)(1)）→ **5D992** 方向。
   該当する場合は年次の自己分類レポート（§742.15(b)、Supplement No. 8 to Part 742）の要否を論点として立てる
7. **License Exception ENC（§740.17）** の適用可否

> §0-2 の申告に従えば多くが手順4の除外方向に落ちるはずだが、**それは仮説であって結論ではない。**
> 1件ずつ手順1から評価し、除外に乗ると判断したものは**乗る根拠と出典**を書くこと。

---

> **なお、本件は SaaS 提供であるため、そもそも「ソフトウェアの export」が発生しないという整理もありうる。
> ただし §4 の `client` 区分（ブラウザに配信されるバンドル）については、その整理が通らない可能性がある。
> この論点はレポートの冒頭に必ず明示し、法務・輸出管理部門の判断を仰ぐ事項として立てること。**

### 6-2. 外為法側のデシジョンツリー

1. **輸出令別表第1（貨物）／外国為替令別表（技術）の該当性** — 情報セキュリティ関連は 9の項。
   §0-4 のとおり、`full` では **対応する貨物等省令の条項番号と技術的閾値まで Web で裏を取る**。
   **条項番号を記憶で書かない。** 出典 URL と取得日を必ず併記し、確認できなければ `要確認` に落とす
2. **適用除外** — 「一般に入手可能なプログラム」「公知の技術」等。OSS の多くはここで落ちる
3. **リスト規制に非該当の場合** → キャッチオール規制（大量破壊兵器／通常兵器）の用途要件・需要者要件
4. **役務取引・みなし輸出** — §0-3 のとおり現状は該当なしと整理する。
   ただし「外国籍メンバーの参画・海外委託が発生した時点で再判定が必要」と明記する（2022年改正の「特定類型」）

### 6-3. 判定を書くときの絶対ルール

- **ECCN・項番を推測で断定しない。** 根拠が特定できないものは必ず `要確認` とし、何を確認すれば決まるかを書く
- 確信度は `高` / `中` / `低` の3段階で必ず付ける
  - `高` = 公式ドキュメントまたは条文の明示的根拠あり
  - `中` = 技術的性質から合理的に導けるが、一次情報の裏付けはない
  - `低` = 推定。判定担当者の確認が必須
- 条文番号・ECCN・省令の条項を書くときは、**出典を併記**する。出典を示せないなら書かない
- 「問題なし」で終わらせない。**該当なしと判断したものも、判断した根拠とともに記録する**（該非判定では「非該当の根拠」が成果物）
- **§0 の申告値を根拠として使ってよいのは「ユーザー申告」と明示したときだけ。** 申告を技術的裏付けのように書かない

## 7. Web 検索の使いどころ（`full` / `diff` のみ）

必要に応じて自由に裏を取ってよい。ただし**判断が割れる項目に絞る**こと。明らかに規制と無関係なユーティリティ（`lodash`, `date-fns`, `classnames` 等）で検索しない。

検索してよい対象：

- 暗号関連パッケージの公式ドキュメント・README（実装アルゴリズムと鍵長の確認）
- パッケージの開発元・原産国（米国原産かどうかの判断材料）
- **ベンダー製品の公表 ECCN**（AWS / Google / 認証基盤ベンダーの輸出管理ページ）— §5-4 により必須
- BIS の EAR 条文・FAQ・Commerce Control List
- **経済産業省・CISTEC の該非判定関連情報、貨物等省令の該当条項**（§6-2 により必須）

取得した情報は **URL と取得日を必ず記録**し、レポートの参考資料セクションに載せる。
検索で確定できなかったものは、確信度を下げて `要確認` に落とす。

## 8. 並列実行（`full` かつ依存が多い場合）

推移依存が 200 件を超える場合は、Task ツールでサブエージェントに分割して調査する。
分割の軸は **カテゴリ別**（暗号関連／クラウド SDK／UI・ユーティリティ／ビルドツール）とし、
ファイル範囲では分けない（依存関係が切れるため）。
各サブエージェントには §0 の前提と §6-3 の絶対ルールをそのまま渡すこと。

## 10. `diff` モードの詳細

### 10-1. 前提の確認

`docs/export-control/snapshot.json` を読む。**無い場合**は `AskUserQuestion` で1問：

- header `ベースライン` — 「比較対象の snapshot.json がありません。どうしますか？」
  - `full を実行してベースラインを作る` / `quick として走る` / `中止する`

### 10-2. 差分の抽出

snapshot と現状を突き合わせ、次を抽出する：

| 差分の種類         | 抽出方法                                                                 |
| ------------------ | ------------------------------------------------------------------------ |
| 追加された依存     | 現状にあり snapshot に無い                                               |
| 削除された依存     | snapshot にあり現状に無い                                                |
| バージョン変更     | 名称一致・バージョン不一致（**メジャー変更は暗号実装の変化を疑う**）      |
| 自社コードの変更   | `git diff <snapshot.commit>..HEAD --name-only` で §5-1 の走査対象に触れたファイル |
| インフラ定義の変更 | 同上。IaC・Dockerfile・CSP・`index.html` の変更                          |

**差分が一切なければ、ファイルを作らずチャットに1行だけ返して終わる。**

### 10-3. 判定

抽出した差分だけを Phase 2（§4）→ Phase 3（§5）→ Phase 4（§6）にかける。
判定の絶対ルール（§6-3）と Web 検索の方針（§7）は `full` と同じ。

**削除された依存も必ず記載する**（「前回 5D992 候補だった ◯◯ が除去された」は判定担当者にとって重要な情報）。

### 10-4. 出力

ファイル名：`docs/export-control/<YYYY-MM-DD>_<HASH>_ear-judgement-diff.md`

構成：比較元コミット／比較先コミット／追加・削除・変更の一覧／新たに立った論点／要確認事項。

書き終えたら `AskUserQuestion` で1問：

- header `snapshot更新` — 「差分の判定結果を snapshot.json に反映しますか？」
  - `反映する（次回の diff は今回の結果を基準にする）` / `反映しない（full で確定させるまで基準を動かさない）`

「反映しない」を選んだ場合、次回の `diff` でも同じ差分が再度報告される。
その旨をチャットで1行伝えること。

## 11. やってはいけないこと

- ECCN や省令の条項を**記憶や雰囲気で断定する**こと
- 「おそらく問題ないでしょう」のような、根拠のない安心を与える結論を書くこと
- 検出できなかったカテゴリを**沈黙で省略**すること（「該当なし」と明記する）
- import の存在だけで暗号該当と判定すること（必ず用途まで確認する）
- **§0 の申告値に合わせて走査結果を丸めること**（矛盾は矛盾として書く）
- 法的助言として読める書き方をすること
- ユーザーの許可なく `npm install` やビルドを実行すること
- **§0 で確定済みの事項を走査開始前に聞き直すこと**
- 質問するとき、選択肢を出さずに自由記述で投げること
